# 测试规则

这份文档用来规定：以后每次新增或修改功能时，应该优先补哪一层测试。

## 默认原则

- **先单测，再集成测试，最后 E2E**
- 纯逻辑优先用单测
- 页面交互和多个模块联动优先用集成测试
- 核心业务主流程、跨页面流程、真机依赖强的功能必须补 E2E

## 什么功能写单测

适合单测的内容：

- 纯函数
- 版本比较
- 字符串/数据格式转换
- 校验规则
- 状态计算
- 条件分支判断
- 不依赖真实网络、真实页面、真实设备的逻辑

判断标准：

- 输入固定，输出也固定
- 不需要真实 UI
- 不需要真实接口

## 什么功能写集成测试

适合集成测试的内容：

- 页面级交互
- 表单提交
- 路由跳转
- 网络请求 + UI 状态变化
- 存储 + 业务逻辑联动
- 权限申请后的页面表现

判断标准：

- 需要 mock 外部依赖
- 但要验证多个组件或模块之间的协作
- 重点看“组合后是否正确工作”

## 什么功能写 E2E

必须做 E2E 的内容：

- 登录 / 注册
- 支付 / 下单
- 内容发布
- 强制更新拦截
- 深链打开
- 推送通知后的跳转
- 其他影响核心业务成败的完整链路

判断标准：

- 用户会连续操作多个步骤
- 任何一步错了都会影响核心结果
- 只看单个函数或单个页面不够

## 默认执行规则

- 新增一个纯逻辑：必须补单测
- 新增一个页面功能：至少补集成测试
- 新增一个关键用户路径：必须补 E2E
- 同一个功能可以同时覆盖三层测试
- 不要为了覆盖率重复测同一件事

## 例外情况

以下情况可以适当放宽：

- 纯视觉样式调整
- 纯文案修改
- 静态布局微调
- 只影响开发调试的页面
- 一次性临时功能

以下情况不能只靠手测：

- 登录
- 支付
- 数据丢失风险
- 更新拦截
- 任何会影响线上用户决策的功能

## 开发时怎么用这份规则

每次开始写功能前，先判断它属于哪一层测试：

1. 是纯逻辑吗？先写单测
2. 是页面联动吗？补集成测试
3. 是核心链路吗？再补 E2E

如果不确定：

- 默认按更高一层处理
- 不要默认降级成只手测
